# Cost and polling experiments

Pass: deterministic delay-policy and regional-unit tests. Regenerate only the new evidence with `node src/cloud/tools/cost085.cjs`. The original `cloud:cost` harness and cloud-084 artifacts remain available unchanged.

Pricing units were checked against the official [Firestore Standard table](https://cloud.google.com/firestore/pricing), [Cloud Run request-based table](https://cloud.google.com/run/pricing), and [Firebase plan table](https://firebase.google.com/pricing) on 2026-11-07. The existing regional table correctly converts per-100,000 document rates to per-document rates; Firestore storage uses GiB and shared daily quotas. Functions v2 uses request-based compute allowances, which differ from the generic first-generation Firebase table. Billing-account-wide Cloud Run allowances and one eligible Firestore database are assumed. No rates were changed.

All numbers below are workload estimates, not measurements of real users. The same 30-day workload applies to each comparison: 30 logical actions/user/day, 500 tasks/workspace, 80% independent task edits and 20% complex edits retaining full validation, three messages/day and five watchers. Mutations compare six reads/five writes for the ordinary title/description/priority path (custom values need a seventh configuration read) against 508 reads/six writes. Retained complex-path costs remain conservative. No consolidation savings are assumed in these projections, and function duration stays at the same 0.25-second assumption in all variants. Actual mixed-project structural costs vary with Canvas/governance records. Every new comparison variant additionally includes one post-Save reconciliation request per logical action: 30/user/day, four reads/request, with the same function request/compute assumptions. The optimized journal can use a three-read warm pull after a safe contiguous acknowledgment; four reads is retained conservatively for both versions and covers rereading one changed task. Unseen multi-record collaboration updates may cost more. Set `postSaveRefreshesPerUserDay` and `postSaveRefreshReads` explicitly for another workload; historical 084 projection variants remain unchanged.

An unchanged 20-minute workspace session previously generated 240 five-second polls; the new deterministic policy generates 22. An unchanged six-minute open conversation previously generated 120 three-second polls; the new policy generates 14. Periodic requests modeled fall from 360 to 36 per user/day (90%), excluding saves, post-Save reconciliation and messages. Including 30 commits, 30 reconciliation requests and three message sends, total modeled requests fall from 423 to 99/user/day (76.6%). Changed sessions reset the policy and generate more requests. Modeled savings do not establish observed real-user traffic savings. Maximum unchanged foreground visibility bounds rise to 60 seconds/workspace and 30 seconds/conversation; returning from background refreshes immediately. Hidden/background checks use 120 seconds. Fresh permission checks still occur on every network read.

The JSON/CSV also isolate mutation-only and polling-only optimization and a stress assumption that doubles mutation read attempts. Stress is a model, not measured production contention. It does not estimate CPU autoscaling cost from emulator throughput.

These are incomplete infrastructure subtotals. Spark does not support this Functions-based production architecture. Blaze allowances are modeled without activating billing; backup/PITR/restore/clone have no free allowance. Build, registry, logs, App Check provider, enterprise identity, bucket selection, real indexes, full transfer behavior and other unspecified usage remain unpriced or zero input. A zero modeled input does not establish a service is free. Never use this subtotal as a complete Firebase bill.

The benchmark also compares a 45-second checkpoint with a ten-minute strategy: 300 compatible local edits over ten minutes model 14 versus one cloud mutation, with maximum checkpoint staleness increasing from 45 to 600 seconds. Explicit Save/close/status commits can increase both counts. Ten minutes remains an experiment, not the default. Durable local persistence occurs independently of checkpoint frequency.
