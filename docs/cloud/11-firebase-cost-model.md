# Firebase cost model

Run npm run cloud:cost, or pass a replacement region price-table path after --. The checked-in us-central1 table is dated 2026-11-07; rates carry units, source URLs, allowances and assumptions. Cost functions reject invalid usage and flag positive usage without configured prices. JSON/CSV projections cover 100/1,000/10,000/100,000 active users and five strategies: full record resave, incremental, cache, summaries and high concurrency.

Firestore document/index-batch/rule-dependent reads share one project allowance. Daily quotas are modeled with flat daily workload; bursty workloads need per-day calculation. Storage includes an explicit index/metadata assumption rather than pretending JSON bytes equal billed size. Current code uses trusted server reads, so client rules-dependent reads are zero for that path; direct client queries need their own count. Listener fan-out is an assumption and cannot be equated with one user action.

The table distinguishes Spark availability, Blaze free allowances and first-use charged backup/PITR/restore/clone. This Functions-based architecture cannot run in production on Spark, even when projected usage fits a quota. No billing upgrade occurs here. Functions v2 compute uses Cloud Run request-based allowances, not a mixture with first-generation CPU/GB-second quotas. Network prices depend on destination; the default transfer rate is a configurable assumption. Build/container/logging/event/Scheduler/Secret Manager/App Check/Cloud Storage/enterprise identity components are explicit inputs and remain unpriced until selected. Zero input means unused, not universally free.

Projections assume 30 days, 30 committed actions and 240 five-second active-session polls per user/day, 500 records plus eight conservative overhead reads per mutation, 120 conversation polls and three messages per user/day, five authorized watchers per message, 0.25 s function duration, 0.25 GiB allocated memory, 60% paid seats and ten users per organization. Conversation polling models seven reads per page request and messages include authorization fan-out and notification writes. These are workload assumptions, not measured user behavior or commercial pricing. Polling/auth checks and broad validation are included; client payload savings do not erase them. Known subtotal is labeled separately from unpriced components. Cost per user/org/paid seat divides the projected infrastructure subtotal only.

Sources: [Firebase plans](https://firebase.google.com/pricing), [Firestore Standard pricing](https://cloud.google.com/firestore/pricing), [Cloud Run request-based pricing](https://cloud.google.com/run/pricing). Emulator counters are local instrumentation, never certified billable counts. Confirm region, complete service selection, real listener traffic, retry behavior and billing-account allowance sharing before relying on a production estimate.
