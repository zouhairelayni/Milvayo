# Canvas and collaboration

Canvas metadata, objects, connectors and anchored threads are independent records. Committed element movement updates that element and any changed board metadata; gesture previews, pointer events and panning stay local. Existing geometry ledgers, connector attachment, camera code, inline commit buffering, undo/redo and import/export are preserved. Reconciliation validates the complete project before replacing local state. Same-element field conflicts are detected; thread message arrays and rich text are indivisible conflict units.

Task sheets and Canvas editors show other active viewers and a soft editing warning through a shared presence hook. Presence uses per-user/per-session RTDB children, server time offset, a 60-second expiry, 25-second heartbeat, and onDisconnect cleanup. Multiple sessions do not share one online boolean. Read/write authorization is project-scoped; no Firestore write is generated by a heartbeat. RTDB authorization projection expiry is 90 seconds and is renewed from fresh backend access checks. Signals are warnings, not exclusive locks.

Canonical task comments and Canvas thread replies synchronize through their existing record paths. Legacy local author labels remain compatible; the trusted cloud actor is recorded separately. Collaboration → Cloud conversations adds project/task discussions, self-watch controls, authorized member mentions, typing/viewer signals, and pointer-only notifications. Messages use authenticated actor UIDs and their own immutable, paginated records. Sends use the same durable ordered journal and actor-bound idempotency IDs as other cloud operations. The server rechecks each recipient’s current read access; revoked watchers are skipped and unauthorized mentions are rejected. Notifications never contain a confidential message body. Directory results expose only authorized shared display names and UIDs. Legacy local comments remain separate and compatible.

Host benchmarks exercise 25/100/500/1,000 objects and show granular payload changes. The existing board limit is 1,000 objects: larger Canvas workloads are bounded simulations, not a claim that the UI supports thousands per board. Actual Android pan/zoom/FPS, multi-device editing and dropped-network onDisconnect timing still require device acceptance. Cloud sharing does not reinterpret the Canvas local-owner sentinel as an identity or enable its old grants array.
